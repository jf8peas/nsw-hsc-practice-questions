# Feature Specification: Learn From Mistakes

**Feature Branch**: `002-learn-from-mistakes`

**Created**: 2026-10-28

**Status**: Draft

**Input**: User description: "Learn From Mistakes: help students learn the concepts they get wrong, and practise them until they have learned them. Every quiz outcome is stored (already true from spec 001). Every question carries a concept tag from a per-unit list of concepts. Concept ids are never renamed or reused. Each concept has a count of correct answers still needed: any wrong answer sets it to 3, a correct answer on any question with that concept tag takes 1 away, and at 0 the concept is cleared. Each unit page shows a personalised \"Things you need to know\" summary for that unit: the student's uncleared concepts, highest count first, ties broken by the most recently missed, always reflecting the student's current state. Each concept's summary explains the concept itself, not why a specific answer was wrong; it is generated by an LLM once per concept, checked by an independent reviewer before any student sees it, stored, and reused for all students. The LLM decides whether a concept needs an illustration; if so, a dedicated illustration model generates one, also reviewed, stored and reused. Concept generation has its own daily cap, separate from grading; if generation or review fails or the cap is reached, the unit page still lists weak concepts by their one-line descriptions. A teacher can review and regenerate any concept's summary or illustration. There is no separate retest: every normal quiz in a concept-ready unit fills half its places (rounded up) with questions on the student's uncleared concepts, highest count first and unseen questions first, and the rest are drawn as usual. Questions come only from the unit's existing bank, and these quizzes count normally toward averages, best, latest and trend. Per-question feedback: MC wrong options each have a written explanation in the server-only answer key, shown after answering; short-answer feedback stays generated by the LLM grader and saved with the result. Writing the MC wrong-option explanations is content work, done unit by unit. Must comply with constitution 2.9.1."

## Clarifications

### Session 2026-10-28

- Q: Which concept tag does a past result count against? → A: The question's current tag, worked out when concept progress is read. Nothing extra is stored per result, so corrected tags apply to history, and results from before a unit was tagged count once it is.
- Q: What does a student see while a concept's summary is generated on first view? → A: The one-line description straight away. Generation runs in the background, and the summary appears on the same page when ready, or on the next visit. The student never waits on the generator.
- Q: Do students see newly generated content before it has been reviewed? → A: No. Every summary and every illustration must first pass an independent reviewer (a different model from the generator). Only approved content is ever shown; until then, or if an item fails review twice, students see only the one-line description. (Replaces the earlier answer that content was shown immediately with no approval step, to match constitution 2.5.0.)
- Q: Is there a separate retest? → A: No. Every normal quiz in a concept-ready unit fills half its places (rounded up) with questions on the student's uncleared concepts, and the rest are drawn as usual. These quizzes count normally toward averages, best, latest and trend, and are not labelled. This replaces the separate retest attempt.
- Note (from the user): Quiz questions come only from the unit's existing question bank. No quiz question is written by the LLM.
- Q: How many of a quiz's places go to weak concepts? → A: Exactly half, rounded up (a 10-question quiz weights 5; a 3-prompt quiz weights 2), whenever enough weak-concept questions exist. This replaces the earlier "up to half, rounded down" cap.
- Q: What if exact half and the unit's usual MC/short-answer mix conflict? → A: Exact half wins. The usual mix is kept only as far as it does not reduce the weak-concept places.
- Q: If a teacher regenerates approved content and the replacement fails review twice, what do students see? → A: The previously approved version stays on show; the failed replacement is flagged for the teacher.
- Q: How does a teacher fix a flagged item and mark it approved? → A: Directly in the backend, as with the teacher queries in spec 001. The review page lists and regenerates; it has no in-app editing.
- Q: Must every unit be fully tagged and explained before the feature ships? → A: No. Units adopt concepts and MC explanations one at a time. A unit is marked concept-ready once all its questions are tagged, and explanations-complete once all its wrong MC options have explanations. Unmarked units keep working as before. Constitution 2.6.0 was amended to allow this.
- Q: How do removed questions keep counting, and how is a silent removal or renumbering caught? → A: When a question is removed, the content team records the concept it belonged to, or that it had none if its unit was not yet tagged. Results for a question recorded with no concept count toward none until the unit is tagged and the record is given a concept; a concept-ready unit may not have such records. A committed list of shipped question and concept ids makes the release check fail if a shipped id disappears without that record, and a shipped concept id may never disappear.
- Q: Does partial credit on a short answer count as correct for concept tracking? → A: No. Only full marks counts as correct; any lower mark counts as wrong.
- Q: How do self-marked short answers count for concept tracking? → A: Like any other answer. A wrong self-mark sets the count to 3 and a correct self-mark takes 1 away. Self-marking is a fallback (AI marking failed or the daily cap was reached), not something students choose.
- Q: May the reviewer's stored reason quote model answers or marking criteria? → A: Yes. Because of that, the reason is visible to teachers only, never to students.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Know which concepts I still need to learn (Priority: P1)

Every question in a concept-ready unit belongs to one concept in its unit (for example, "calculating opportunity cost"). As a student answers questions, the app keeps a running count for each concept of how many more correct answers they need before it counts as learned. A wrong answer on any question sets that concept's count to 3. A correct answer on any question with the same concept takes 1 away. When the count reaches 0 the concept is cleared. On the unit page, a "Things you need to know" section lists the student's uncleared concepts for that unit, highest count first, with ties broken by the most recently missed. Each concept shows its one-line description and how many correct answers are still needed. The list always reflects the student's current state, never a snapshot from when a quiz was taken.

**Why this priority**: This is the core of the feature. Without concept tracking there is nothing to summarise, weight quizzes towards or personalise, and even on its own it tells a student exactly where their weaknesses are.

**Independent Test**: Sign in as a student, answer a question wrongly, and open the unit page. Confirm its concept appears with a count of 3. Answer three questions with that concept correctly across one or more quizzes and confirm the count falls 3, 2, 1 and the concept disappears.

**Acceptance Scenarios**:

1. **Given** a student who has never missed a question with concept C, **When** they answer such a question wrongly, **Then** C appears in "Things you need to know" on that unit's page with a count of 3.
2. **Given** C has a count of 2, **When** the student answers any question tagged C wrongly, **Then** its count becomes 3, not 4.
3. **Given** C has a count of 3, **When** the student answers any question tagged C correctly, **Then** its count becomes 2, even if it is a different question from the one they missed.
4. **Given** C has a count of 1, **When** the student answers a question tagged C correctly, **Then** C is cleared and no longer appears in the list.
5. **Given** a cleared concept, **When** the student later answers a question tagged C wrongly, **Then** C returns to the list with a count of 3.
6. **Given** a student with several uncleared concepts in a unit, **When** they open the unit page, **Then** the concepts are ordered by highest count first, and concepts with equal counts are ordered by the most recently missed first.
7. **Given** a student who answered a question wrongly in an earlier quiz, **When** they correctly answer a question with the same concept in a later quiz, **Then** the next time they open the unit page the list reflects both answers, not the state when the first quiz ended.
8. **Given** a student with no uncleared concepts in a unit, **When** they open its page, **Then** they see a short encouraging message instead of an empty list or an error.
9. **Given** a short-answer question marked as partial credit, **When** the student does not earn full marks, **Then** the answer counts as wrong for concept tracking; only full marks counts as correct.
10. **Given** two different students, **When** one misses a concept, **Then** the other student's list is unaffected.

### User Story 2 - Relearn a concept from a clear explanation (Priority: P1)

Beside each concept in "Things you need to know", the student can open a short explanation of the concept itself: a few bullet points on what they need to understand. It explains the idea in general, not why a specific answer was wrong, and never gives away any question's answer. Where a concept is easier to grasp with a picture, the explanation also includes an illustration. Each concept's explanation is written once, checked by an independent reviewer before any student sees it, stored, and shown to every student, so students see the same explanation and it appears instantly.

**Why this priority**: Telling a student which concepts are weak is only half the value; the explanation is what lets them relearn it. It is P1 because practice without relearning is just repetition.

**Independent Test**: With an approved explanation for a concept, miss a question on that concept as two different students and confirm both see the identical explanation from the unit page, without any wait for generation.

**Acceptance Scenarios**:

1. **Given** a student with an uncleared concept that has an approved explanation, **When** they open it from the unit page, **Then** they see the approved bullet points and illustration (if one exists and is approved) immediately.
2. **Given** an uncleared concept that has no approved explanation yet, **When** a student opens the unit page, **Then** they see the concept's one-line description immediately; the system generates the explanation once in the background, has it reviewed, and stores it; and it appears on the same page (or on their next visit) once approved. A second student opening the same concept gets the stored one without a new generation.
3. **Given** a concept whose explanation was judged to need an illustration and whose illustration is approved, **When** the student views the explanation, **Then** the illustration is shown with the bullet points, and it carries a text description for students who cannot see images.
4. **Given** a concept judged not to need an illustration, **When** the student views the explanation, **Then** only bullet points are shown and no empty image area appears.
5. **Given** any explanation shown to students, **When** a student reads it, **Then** it explains the concept in general terms and does not reproduce any question's model answer, marking criteria or correct multiple-choice option.
6. **Given** an explanation was generated for one student's weakness, **When** another student views the same concept, **Then** nothing about the first student (answers, name, history) is present in it.

### User Story 3 - Always be able to see weak concepts, even when generation or review fails (Priority: P1)

If an explanation or illustration cannot be produced or approved (the generator or reviewer is unavailable, it fails, or the daily limit on concept generation has been reached), the unit page still lists the student's weak concepts by their one-line descriptions with their counts. No error is shown, and the student can still start a quiz. Generating and reviewing explanations has its own daily limit, separate from the limit on AI marking of short answers, so a busy day of explanations never uses up a student's marking allowance and vice versa.

**Why this priority**: The constitution requires practice to degrade gracefully. This guarantees the feature never blocks a student and that generation and review costs are bounded.

**Independent Test**: Switch off the generator (or set the generation limit to 0), then open a unit page with uncleared concepts that have no approved explanation. Confirm the list shows one-line descriptions, no error, and a quiz can still be started. Confirm short-answer AI marking still works.

**Acceptance Scenarios**:

1. **Given** the generator is unavailable, **When** a student opens a unit page with an uncleared concept that has no approved explanation, **Then** the concept is listed by its one-line description and count, with no error.
2. **Given** the daily generation limit has been reached, **When** a student opens a concept with nothing approved, **Then** they see the one-line description, and nothing new is generated or reviewed until the limit resets.
3. **Given** the daily generation limit has been reached, **When** a student submits a short answer, **Then** AI marking works exactly as before, because the two limits are independent.
4. **Given** the daily AI-marking limit has been reached, **When** a student opens a concept with nothing approved, **Then** the explanation can still be generated and reviewed, because the two limits are independent.
5. **Given** a concept that already has an approved explanation, **When** the generation limit has been reached, **Then** the approved explanation is still shown, because showing stored content costs nothing.
6. **Given** a generation that failed, **When** a later student opens the same concept, **Then** the system may try again (subject to the limit) and a failed or unreviewed item is never shown as if it were good content.

### User Story 4 - Quizzes focus on what I got wrong (Priority: P2)

In a unit marked concept-ready, every normal quiz gives half its places (rounded up) to questions on the student's uncleared concepts in that unit. Those places go to the highest-count concepts first and to questions the student has not seen before, with no single concept taking every weighted place while others have questions available. The rest of the places are drawn as usual, and the unit's usual mix of multiple-choice and short-answer questions is kept as far as it does not reduce the weak-concept places. A student with no uncleared concepts, or a unit that is not concept-ready, gets a normal quiz. There is no separate retest: the quiz counts normally in history, averages, best, latest and trend, and is not labelled. Answers update concept counts like any other quiz, so ordinary practice is how a student clears concepts.

**Why this priority**: This closes the loop: identify, relearn, practise. It depends on Stories 1 and 2 to be useful, but a student could already benefit from stories 1 to 3 without it.

**Independent Test**: Miss questions on two concepts in a unit, start a quiz in that unit, and confirm half its questions (rounded up) are tagged with those concepts and the rest are drawn as usual, unseen weak-concept questions are chosen first, and after answering correctly the concept counts fall. Confirm the quiz appears in history like any other and is not labelled.

**Acceptance Scenarios**:

1. **Given** a student with enough questions available on their uncleared concepts in a concept-ready unit, **When** they start a quiz, **Then** exactly half its places (rounded up) go to questions on those concepts, even if that changes the unit's usual MC/short-answer mix.
2. **Given** fewer questions available on the student's uncleared concepts than half the quiz, **When** the quiz is built, **Then** all of them are included and the remaining places are drawn as usual.
3. **Given** both unseen and already-seen questions on the uncleared concepts, **When** the weighted places are chosen, **Then** unseen questions come first, and seen questions fill the remaining weighted places only when there are too few unseen, preferring those answered wrongly or least recently.
4. **Given** several uncleared concepts, **When** the weighted places are chosen, **Then** the highest-count concepts come first (ties broken by the most recently missed), and no single concept takes every weighted place while others have questions available.
5. **Given** a unit that normally mixes multiple-choice and short-answer questions, **When** a weighted quiz is built, **Then** the usual mix is kept as far as it does not reduce the weak-concept places below half (rounded up).
6. **Given** a student with no uncleared concepts in a unit, **When** they start a quiz, **Then** it is a normal quiz with no weighting.
7. **Given** a unit that is not marked concept-ready, **When** a student starts a quiz, **Then** it is a normal quiz with no weighting and no error.
8. **Given** a weighted quiz, **When** the student answers questions, **Then** concept counts change by the same rules as in Story 1, cleared concepts drop out of the "Things you need to know" list, and the quiz counts normally in history, averages, best, latest and trend, with no label.
9. **Given** a student who abandons a weighted quiz part-way, **When** they return, **Then** they can continue it like any other incomplete quiz, with the same questions, and the answers already given are kept and counted.
10. **Given** a weighted quiz, **When** it is built, **Then** every question comes from the chosen unit's existing question bank and none comes from another unit.

### User Story 5 - Understand why each wrong option is wrong (Priority: P2)

In a unit marked explanations-complete, after a student answers a multiple-choice question, the app shows an explanation of why the option they chose was wrong (when it was) next to the correct answer. Every wrong option has its own written explanation. The explanations are written by the content team, unit by unit, and are never sent to the browser before the student has answered that question. Short-answer feedback is unchanged: it is generated by the AI marker and saved with the result.

**Why this priority**: Per-question feedback complements concept summaries (which explain concepts, not specific answers). It is valuable on its own, but the feature is usable without it, and it needs substantial content work, so it is delivered unit by unit.

**Independent Test**: In a unit with explanations written, answer an MC question wrongly and confirm the explanation for the chosen option appears only after answering. Inspect what the browser receives before answering and confirm no explanation is present.

**Acceptance Scenarios**:

1. **Given** a student who has just answered an MC question wrongly, **When** the mark is shown, **Then** they also see the written explanation for the option they chose.
2. **Given** a student who has not yet answered an MC question, **When** the page loads, **Then** nothing sent to their browser contains any option's explanation.
3. **Given** a student who answers an MC question correctly, **When** the mark is shown, **Then** no wrong-option explanation is shown, and the explanations for the other options are not revealed.
4. **Given** a student reviewing a past attempt, **When** they open an MC question they answered wrongly, **Then** they see the current explanation for the option they chose; explanations are not stored per result.
5. **Given** a short-answer question, **When** it is marked by the AI marker, **Then** the feedback is generated as it is today and saved with the result.
6. **Given** a unit whose explanations have not yet been written, **When** a student answers an MC question wrongly, **Then** the app behaves as it does today, with no error and no empty explanation area.
7. **Given** a question with a wrong option that has no explanation, **When** the content is validated before release, **Then** the problem is reported and the release does not proceed for units marked explanations-complete.

### User Story 6 - Teacher reviews, regenerates and approves concept content (Priority: P3)

A teacher (a person on the teacher allow-list) can open a review page listing every concept across units with its summary and illustration, each one's review status and the reviewer's reason, and who/what produced them and when. They can regenerate any concept's summary or illustration if it is poor, unclear or wrong; the new version goes through the independent review again before students see it. Items that failed review twice are flagged and found with a documented query in `docs/teacher-queries.sql`. A teacher can fix a flagged item and set it to approved in the backend, after which it is shown to students. Students and non-allow-listed signed-in users cannot reach the page or any of its actions.

**Why this priority**: Because one stored explanation serves every student, quality control matters; but the feature works without this page, so it is lowest priority.

**Independent Test**: Sign in as a teacher, open the review page, regenerate one concept, and confirm the new content is reviewed and, once approved, replaces the old for a student who views it afterwards. Sign in as a non-teacher and confirm neither the page nor the regenerate action is accessible.

**Acceptance Scenarios**:

1. **Given** a signed-in teacher, **When** they open the review page, **Then** they see every concept with its summary, illustration (if any), generation time, review status and the reviewer's reason.
2. **Given** a teacher viewing a concept, **When** they ask to regenerate its summary or its illustration, **Then** new content is generated and reviewed, and replaces the approved content for all students only once it is approved.
3. **Given** a regeneration that fails, fails review twice, or is over the generation limit, **When** the teacher requests it, **Then** the existing approved content stays on show, the failed replacement is flagged, and the teacher sees why it did not change.
4. **Given** a signed-in student who is not on the teacher allow-list, **When** they open the review page address or send a regenerate request by any means, **Then** they are refused and nothing is changed or revealed.
5. **Given** a concept with no stored content yet, **When** the teacher opens the review page, **Then** it is shown as "not generated" with an option to generate it.
6. **Given** a regenerated concept whose new content has been approved, **When** a student next opens it, **Then** they see the new content with no stale copy.
7. **Given** items flagged after failing review twice, **When** the teacher runs the documented flagged-items query, **Then** each flagged item is listed with its concept, review status and the reviewer's reason.
8. **Given** a flagged item the teacher has fixed and set to approved in the backend, **When** a student next opens that concept, **Then** they see the fixed content, recorded as approved by a teacher.

### User Story 7 - Students only see reviewed content (Priority: P1)

Before any concept summary or illustration reaches a student, an independent reviewer (a different model from the one that generated it) checks it against the concept's description and the unit's model answers and marking criteria. For illustrations it also checks labels, axes and shapes. The text and the illustration are reviewed separately. Content that fails is regenerated once automatically; if it fails again it is held back and flagged for the teacher, and students see only the concept's one-line description.

**Why this priority**: Generated content is shown to minors and to every student at once, so an unchecked mistake would spread widely. The constitution requires this review before any student sees content.

**Independent Test**: Force a generated item to fail review twice and confirm no student ever sees it, the concept shows only its one-line description, and the item is flagged with its status and reason. Force a pass and confirm it is shown.

**Acceptance Scenarios**:

1. **Given** a newly generated summary, **When** the reviewer checks it and it passes, **Then** it is marked approved and shown to students.
2. **Given** a generated item that fails review the first time, **When** the system regenerates it once and the new version passes, **Then** the new version is approved and shown, and the version that failed is never shown.
3. **Given** a generated item that fails review twice, **When** a student opens the concept, **Then** they see only the one-line description, the item is flagged with status "failed review" and the reviewer's reason, and no email or notification is sent.
4. **Given** the reviewer is unavailable, over the daily generation limit, or set to the same model as the generator, **When** a student opens a concept with unreviewed content, **Then** the content stays "pending review" and is not shown, the student sees one-line descriptions with no error, and students can still start quizzes.
5. **Given** content left pending because the reviewer was unavailable or capped, **When** a student next opens the concept and the reviewer is available and under the limit, **Then** the review is retried.
6. **Given** a concept whose summary passes review but whose illustration fails twice, **When** a student opens the concept, **Then** they see the summary without the illustration and no empty image area, and the illustration is flagged.
7. **Given** an illustration with a wrong label, axis or shape, **When** the reviewer checks it, **Then** it fails review.

### Edge Cases

- **Concept with no questions answered yet**: a concept the student has never been asked about is never listed; only concepts where the student has answered wrongly (and not yet cleared) appear.
- **Retired questions**: a question removed from a unit still counts toward concept history already recorded, but retired questions are never drawn for a quiz.
- **Fewer weak-concept questions than half**: if the bank has fewer questions on the student's uncleared concepts than half the quiz, all of them are used and the remaining places are drawn as usual; the quiz is never padded with questions from another unit.
- **Odd-sized quizzes**: half is rounded up, so a quiz of three questions weights two.
- **Concept cleared mid-quiz**: if a concept is cleared partway through a quiz, remaining questions on it stay in that quiz; the concept's list entry simply disappears afterwards.
- **Same concept answered twice in one quiz**: each answer counts in order. A wrong answer then a correct one leaves the count at 2; a correct answer then a wrong one leaves it at 3.
- **Two devices at once**: answers from both devices are all counted, and the final count is the same no matter the order in which the answers arrive and are saved.
- **Concept tag change**: if a question's concept tag is corrected later, all of the student's past results on that question count against the new tag, because the tag is looked up from the question when progress is worked out. Concept ids themselves are never renamed or reused.
- **Results from before a unit was tagged**: a student's earlier results in a unit (from spec 001) count toward concept progress as soon as the unit's questions are tagged.
- **Database temporarily unreachable**: practice continues as in spec 001. The unit page cannot show a personalised list and says so plainly, without an error. Concept progress is calculated from saved results once they are saved.
- **Database unreadable at quiz start**: weighting needs the student's saved results, so the quiz still starts but is drawn without weighting, as an ordinary quiz.
- **Illustration unavailable or not approved**: a concept whose illustration cannot be shown still shows its bullet points.
- **Reviewer unavailable or misconfigured**: if the reviewer cannot be reached, is over the generation limit, or is set to the same model as the generator, new content stays pending and is not shown; students see one-line descriptions with no error.
- **Replacement fails review**: when a teacher regenerates approved content and the replacement fails review twice, the previously approved version stays on show and the replacement is flagged.
- **Deleted student**: all concept progress disappears with the student's results, because it is derived from them.
- **Time zones**: the generation daily limit resets at midnight Sydney time, like the AI-marking limit.
- **Concurrent first views**: if two students open the same ungenerated concept at the same moment, the concept is generated, and reviewed, once, not twice.

## Requirements *(mandatory)*

### Functional Requirements

**Concepts and tracking**

- **FR-001**: Each concept-ready unit MUST define a list of concepts, each with a permanent id and a one-line description.
- **FR-002**: Every question in a concept-ready unit MUST carry exactly one concept tag, drawn from its own unit's list.
- **FR-003**: Concept ids MUST NEVER be renamed or reused once shipped. The release check MUST fail if a shipped concept id disappears.
- **FR-004**: The system MUST track, per student and concept, a count of correct answers still needed. A wrong answer on any question with that concept's tag MUST set the count to 3; a correct answer on any such question MUST reduce it by 1; the count MUST never go below 0 or above 3; at 0 the concept is cleared.
- **FR-005**: For short answers, only full marks MUST count as correct for concept tracking; any lower mark counts as wrong. Self-marked answers count the same way as automatically marked ones.
- **FR-006**: A student's concept counts MUST be derived from their stored results, using each question's current concept tag (or, for a question that has since been removed, the concept recorded for it when it was removed; if it was recorded as having none, its results count toward no concept), so there is no separate per-student concept record and no tag stored per result, and deleting a student's results removes their concept progress.
- **FR-007**: The concept count MUST be the same regardless of the order in which results are saved, when results are replayed in the order the answers were given.
- **FR-008**: Retired questions MUST still count in concept history already recorded. The content team records a removed question's concept when it is removed (or records that it had none, in a unit not yet tagged), so this holds without storing a tag per result, and the release check MUST fail if a shipped question disappears without that record.

**Unit page: Things you need to know**

- **FR-009**: The unit page MUST show a personalised "Things you need to know" section listing the signed-in student's uncleared concepts for that unit only.
- **FR-010**: The list MUST be ordered by highest count first, with ties broken by the most recently missed first.
- **FR-011**: The list MUST reflect the student's current state every time the page is opened, never a snapshot taken at quiz time.
- **FR-012**: Each listed concept MUST show its one-line description and the number of correct answers still needed.
- **FR-013**: When a student has no uncleared concepts in a unit, the page MUST show a short positive message, not an error or an empty list.
- **FR-014**: A student MUST only ever see their own concept list; no request from the client can select another student's data.

**Concept summaries and illustrations**

- **FR-015**: Each concept's summary MUST explain the concept itself in general terms, as bullet points. It MUST NOT explain why a specific answer was wrong, and MUST NOT reproduce any question's model answer, marking criteria or correct multiple-choice option.
- **FR-016**: Each concept's summary MUST be generated once, reviewed, stored and reused for all students. Generation MUST happen only when a concept has nothing stored yet, when a teacher asks to regenerate it, or for the single automatic regeneration in FR-026 or a retry of a pending review (FR-028).
- **FR-017**: The generator MUST decide whether a concept needs an illustration. If so, a separate dedicated illustration generator MUST produce one, which is reviewed, stored and reused in the same way as the summary.
- **FR-018**: Stored concept content MUST be shared content and MUST NOT contain any student's answers, name or other personal data. For each of the summary and the illustration it MUST hold the live approved version plus at most one pending or failed replacement. Each version MUST record the illustration brief and its text description (for an illustration), the generator used, when it was generated, its review status, the reviewer's reason, the reviewer model used, the review time, and who approved it (reviewer or teacher).
- **FR-019**: Illustrations MUST be shown only as images, never inserted as executable or inline markup, and each MUST have a text description for students who cannot see images.
- **FR-020**: A generation that fails MUST NOT be stored or shown as good content.
- **FR-021**: Generating or reviewing a concept's content MUST NOT delay the unit page: the page MUST render immediately with one-line descriptions, and approved content MUST appear when ready without the student reloading, or on their next visit.
- **FR-022**: If two generation requests for the same concept arrive together, the concept MUST be generated, and reviewed, only once.
- **FR-023**: Approved content MUST be shown without any generation cost or delay, even when the generation limit has been reached.

**Independent review**

- **FR-024**: Every concept summary and every illustration MUST pass an independent reviewer before any student sees it. The reviewer MUST use a different model from the one that generated the item being reviewed. It MUST check the item against the concept's description and the unit's model answers and marking criteria, and for illustrations MUST also check labels, axes and shapes.
- **FR-025**: The summary text and the illustration MUST be reviewed and approved separately. If the text passes and the illustration fails, students MUST see the text without the illustration.
- **FR-026**: An item that fails review MUST be regenerated once automatically. If the regenerated item also fails, it MUST be held back: students see only the concept's one-line description (or, where an earlier approved version is live, that version), and the item MUST be flagged in the database with its review status and the reviewer's reason. The system MUST NOT send emails or notifications.
- **FR-027**: Each item MUST have one of four statuses: not generated, pending review, approved, or failed review. Only approved content MUST ever be shown to students.
- **FR-028**: If the reviewer is unavailable, over the generation limit, or configured as the same model as the generator, content MUST stay pending review and MUST NOT be shown. Students MUST see one-line descriptions with no error, and MUST NOT be stopped from starting a quiz. The review MUST be retried the next time a student opens the concept, subject to the limit. (See also FR-031.)
- **FR-029**: The reviewer's stored reason MAY quote model answers or marking criteria. It MUST be visible only to teachers and MUST NOT be shown to students.

**Limits and graceful degradation**

- **FR-030**: Concept generation MUST have its own daily limit, separate from and not affecting the daily AI-marking limit for short answers, counted per Sydney calendar day. Reviewer calls and automatic regenerations MUST count toward this limit. The limit MUST be configurable.
- **FR-031**: If a summary or illustration cannot be generated or approved (no key, failure, failed review, or limit reached), the unit page MUST still list the student's weak concepts by their one-line descriptions and counts. It MUST NOT show an error and MUST NOT stop the student starting a quiz.
- **FR-032**: The generator's and reviewer's access keys and model choices, including the choice of illustration generator, MUST be kept private to the server and never be sent to or readable from the browser.

**Weighted quizzes**

- **FR-033**: In a unit marked concept-ready, every quiz MUST give exactly half its places (rounded up) to questions on the student's uncleared concepts in that unit, whenever enough such questions exist, and MUST NOT give them more.
- **FR-034**: The remaining places MUST be drawn as usual for that unit.
- **FR-035**: The weighted places MUST go to the highest-count concepts first (ties broken by the most recently missed) and MUST prefer questions the student has not answered before; where there are too few unseen questions, they MUST be filled with questions the student has answered, preferring those answered wrongly or least recently.
- **FR-036**: The weighted places MUST NOT all go to a single concept while other uncleared concepts have available questions.
- **FR-037**: If the bank has fewer questions on the student's uncleared concepts than the weighted places allow, the quiz MUST use all of them and draw the remaining places as usual, without padding from another unit.
- **FR-038**: The unit's usual mix of multiple-choice and short-answer questions MUST be kept as far as it does not reduce the weak-concept places required by FR-033; where the two conflict, FR-033 wins.
- **FR-039**: A student with no uncleared concepts in a unit, or a unit not marked concept-ready, MUST get a normal quiz with no weighting.
- **FR-040**: Quiz questions MUST come only from the unit's existing question bank; the system MUST NOT use an LLM to write any quiz question.
- **FR-041**: A quiz MUST NEVER draw a retired question.
- **FR-042**: A quiz MUST NEVER draw a question from another unit.
- **FR-043**: A weighted quiz MUST count normally in the student's history, unit averages, best, latest and trend, and in the teacher's class averages, and MUST NOT be labelled differently from any other quiz.
- **FR-044**: Answers in a weighted quiz MUST update concept counts by the same rules as any other quiz and MUST be saved like any other result.
- **FR-045**: An incomplete weighted quiz MUST be resumable like any other incomplete quiz, with the same questions, and answers already given MUST still count.
- **FR-046**: If the database cannot be read when a quiz starts, the quiz MUST still start, drawn without weighting.

**Per-question feedback**

- **FR-047**: Every wrong option of every multiple-choice question in a unit marked explanations-complete MUST have a written explanation, held with the other answer-key material that is never sent to the browser.
- **FR-048**: An explanation MUST only be sent to the student after they have answered that question, and only for the option they chose. Explanations MUST NOT be stored per result; a past attempt shows the current explanation.
- **FR-049**: Before release, the system MUST check that every question in a unit marked concept-ready has a valid concept tag, that every concept id is unique, and that every wrong option of every multiple-choice question in a unit marked explanations-complete has an explanation; a unit marked but not meeting this MUST stop the release.
- **FR-050**: Short-answer feedback MUST remain generated by the AI marker and saved with the result, as in spec 001.
- **FR-051**: Units not yet marked concept-ready or explanations-complete MUST keep working as they do today, with no error or blank area; a unit without concept tags offers no "Things you need to know" and no weighting, and a unit without explanations shows no wrong-option explanation.

**Teacher review**

- **FR-052**: Only signed-in users on the teacher allow-list MUST be able to open the concept review page or use any of its actions; the check MUST be made on the server for both the page and every action.
- **FR-053**: The review page MUST list every concept with its summary, illustration (if any), generation time, review status and the reviewer's reason, and show concepts with nothing stored as "not generated".
- **FR-054**: A teacher MUST be able to regenerate any concept's summary or illustration. The new content MUST become the pending replacement and go through review again, and MUST replace the live approved version for all students only once it is approved; regeneration MUST count against the concept generation limit. If the replacement fails or fails review twice, the live approved version MUST stay on show and the replacement MUST be flagged.
- **FR-055**: A failed or over-limit regeneration MUST leave existing approved content unchanged and tell the teacher why.
- **FR-056**: The project MUST include a documented query in `docs/teacher-queries.sql` that lists flagged items (those held back after failing review twice) with their concept, review status and the reviewer's reason.
- **FR-057**: A teacher MUST be able to fix a flagged item and set it to approved in the backend; once approved, it MUST become the live version, be shown to students, and be recorded as approved by a teacher. A teacher-approved item is shown without passing the reviewer again; the record of who approved it is how that is told apart.

**Existing results and privacy**

- **FR-058**: The system MUST NOT store any new per-student or per-attempt fields for this feature.
- **FR-059**: All student data rules from spec 001 (own results only, Australian-region storage, deletion after 2 years, immediate deletion on request) MUST continue to apply to everything this feature uses.

### Key Entities *(include if feature involves data)*

- **Concept**: an idea within a unit that a student needs to understand. Has a permanent id, the unit it belongs to and a one-line description. Many questions share a concept. Never renamed or reused.
- **Concept Tag**: the link from one question to exactly one concept in its unit. A question that has been removed keeps a record of the concept it belonged to, or of having had none if it was removed before its unit was tagged.
- **Concept Progress**: for one student and one concept, the count of correct answers still needed (0 to 3) and when the concept was last missed. Not stored on its own; worked out from the student's saved results.
- **Concept Content**: the shared explanation for a concept. For each of the summary and the illustration it holds the live approved version plus at most one pending or failed replacement. Each version records the generator used, when it was generated, its review status (not generated, pending review, approved, failed review), the reviewer's reason, the reviewer model used, the review time and who approved it (reviewer or teacher); an illustration also has its brief and a text description. Identical for every student; contains no student data. Only approved content is shown to students.
- **Wrong-Option Explanation**: for an MC question, the written reason an incorrect option is incorrect. Kept with the answer key; shown only after answering; not stored per result.
- **Concept Generation Usage**: the number of concept generation, review and automatic regeneration calls made on a given Sydney day, used to enforce the separate daily limit.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After answering a question wrongly, a student sees the matching concept in "Things you need to know" the next time they open the unit page, 100% of the time.
- **SC-002**: A student can go from seeing a weak concept on the unit page to starting a quiz that includes it in two taps or clicks.
- **SC-003**: A concept's approved explanation appears to the student within 1 second of opening it, for 95% of views, because it is not generated per student.
- **SC-004**: A concept's explanation is generated at most once, plus one automatic regeneration after a failed review, unless a teacher requests regeneration; across any number of students there are zero duplicate generations.
- **SC-005**: With the generator or reviewer switched off, or the daily limit reached, 100% of unit page views still list the student's weak concepts with their descriptions, with no error shown.
- **SC-006**: Reaching the concept generation limit never reduces a student's AI-marking allowance, and reaching the AI-marking limit never prevents a stored or new concept explanation from being shown.
- **SC-007**: In a concept-ready unit, when enough questions exist on a student's uncleared concepts, exactly half the quiz's places (rounded up) go to those concepts and never more; and 100% of quiz questions come from the chosen unit.
- **SC-008**: In a test of the pages and data sent to students, no wrong-option explanation is present before the question is answered, and no concept summary contains any question's model answer or correct option.
- **SC-009**: Every non-teacher attempt to open the concept review page or regenerate content is refused, in 100% of tested cases.
- **SC-010**: Every unit that is marked explanations-complete has an explanation for 100% of its wrong MC options; the release is blocked otherwise.
- **SC-011**: 0% of content that failed review twice is ever shown to students.
- **SC-012**: 100% of concept content shown to students has an approved review.

## Assumptions

- The sign-in, stored attempts and stored results from spec 001 are in place and are the only source for working out concept progress.
- A student's concept progress is calculated from their saved results in the order the answers were given. A student who has no saved results has no weak concepts.
- Every question has one concept tag; questions that test several ideas are tagged with the main one. Tagging every existing question is content work done unit by unit, and a unit is marked concept-ready, and only then offers "Things you need to know" and weighted quizzes, once all its questions are tagged.
- Only an answer with full marks counts as correct for concept tracking, because partial credit still shows the idea is not fully understood.
- Half of a quiz's places is rounded up, and exact half takes priority over the unit's usual MC/short-answer mix.
- Weighting is decided when a quiz starts, using the student's saved results at that moment.
- Concept generation and review use the same sign-in-protected, server-only approach as AI marking. The default daily generation limit is set in planning, and is chosen to keep total cost per day bounded irrespective of how many students are signed in.
- The reviewer for an illustration must differ from the illustration generator and must be able to examine images.
- Concept explanations are in English, aimed at NSW HSC students, and grounded in the unit's syllabus and documented sources.
- The teacher allow-list is the existing one used for teacher access in spec 001's constitution rules.
- Fixing a flagged item and setting it to approved is done by the teacher in the backend; the review page does not edit content.
- Writing MC wrong-option explanations is separate content work delivered unit by unit; the feature ships and works for units that do not have them yet, and a unit is only marked explanations-complete (and checked before release) once all its explanations are written.
- A result counts against its question's current concept tag, or against the concept recorded for it if the question has been removed (a question removed before its unit was tagged counts toward no concept); no tag is stored per result.
- Browser-stored scores are not used; all progress comes from the student's account.
- The constitution at version 2.9.1 applies. Where this spec and the constitution disagree, the constitution wins.
